# Деплой на VPS — гайд для агентов

Как выкатить сервер z228 на прод и не сломать ничего вокруг. Адрес сервера, пароли и ключи
в репозиторий **не пишем**: адрес берётся из переменной `Z228_VPS`, секреты живут только на сервере.

## Коротко

```bash
git fetch <remote> && git merge --ff-only <remote>/main   # взять свежий main (там бывают чужие коммиты)
Z228_VPS=user@host scripts/deploy-vps.sh                  # тесты → сборка → бэкап → замена → проверка/откат
git push <remote> HEAD:main                               # только fast-forward
```

Скрипт сам: проверит, что код закоммичен, прогонит `go vet`, `go test`, `node --check`, соберёт
linux-бинарь с версией `<коммит>-vps`, сделает бэкап бинаря и базы, перезапустит **только** `z228`,
проверит `/api/info` и при сбое вернёт прошлый бинарь. `--dry` — всё, кроме заливки.

## Правила (нарушать нельзя)

1. **Трогаем только сервис `z228`.** На VPS работают другие важные процессы (прокси на 443 и т.п.).
   Не перезапускать и не останавливать чужие сервисы, не менять firewall, nginx, systemd-юниты
   других программ, не делать `apt upgrade`, не перезагружать машину.
2. **Вход только по SSH-ключу.** Если ключа нет или ssh спрашивает пароль — остановиться и спросить
   человека. Пароли в чат и в команды не вставлять.
3. **Секреты не печатать.** `/etc/z228.env` (пароль админа) не выводить через `cat`/`grep`/`env`.
   Ключи ИИ лежат в базе — не доставать их. Не коммитить `.env`, ключи подписи, базы, бэкапы.
4. **Не трогать TLS-ключ.** `selfsigned.key` в каталоге данных переиспользуется при каждом старте:
   по его отпечатку (SPKI) десктоп-приложение узнаёт сервер. Новый ключ = у всех сломается вход
   в приложении. Не удалять и не пересоздавать.
5. **Не менять юнит `z228` и `/etc/z228.env` без просьбы человека.** Деплой — это только замена
   бинаря `/usr/local/bin/z228`.
6. **Деплоить закоммиченное.** На сервере должна быть версия из git (`z228 -version` → `<коммит>-vps`),
   иначе потом не понять, что там крутится.

## Как устроено на сервере

| Что | Где |
|---|---|
| Сервис | systemd-юнит `z228` (`DynamicUser`), `ExecStart=/usr/local/bin/z228 -data /var/lib/z228` |
| Настройки | `/etc/z228.env` (`EnvironmentFile`) — только пароль админа, остальное в юните/по умолчанию |
| Данные | `/var/lib/private/z228` (из-за `DynamicUser`; `/var/lib/z228` — ссылка): `z228.db`, `selfsigned.*`, `uploads/`, `backups/` |
| Порты | HTTP 3000, HTTPS 3443, голос (WebRTC) 50000 UDP/TCP |
| Бэкапы деплоя | `/root/z228-backup-<дата>/` — прошлый бинарь `z228.prev` и `z228.db*` |

- Сайт (`web/static`) **вшит в бинарь** (`go:embed`). Любая правка фронтенда = пересборка и деплой.
- Миграции базы применяются сами при старте (`internal/store/extra.go`, `migrate`) — только
  добавляют таблицы и столбцы. Отдельно ничего запускать не нужно.
- `sqlite3` на сервере нет. Смотреть в базу не нужно.
- После рестарта люди переподключаются сами (на пару секунд пропадает голос). Чтобы увидеть новый
  фронтенд, им нужно обновить страницу.

## Если делать руками

То же, что делает скрипт (Git Bash / Linux, из корня репо):

```bash
VER="$(git rev-parse --short HEAD)-vps"
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=$VER" -o /tmp/z228-linux ./cmd/server
scp /tmp/z228-linux "$Z228_VPS:/tmp/z228-new"
ssh "$Z228_VPS" 'set -e
  chmod +x /tmp/z228-new && /tmp/z228-new -version
  BK=/root/z228-backup-$(date +%Y%m%d-%H%M%S); mkdir -p $BK
  cp -a /usr/local/bin/z228 $BK/z228.prev; cp -a /var/lib/private/z228/z228.db* $BK/
  install -m 755 /tmp/z228-new /usr/local/bin/z228 && rm /tmp/z228-new
  systemctl restart z228; sleep 3
  systemctl is-active z228 && /usr/local/bin/z228 -version
  curl -fsS http://127.0.0.1:3000/api/info'
```

## Откат

```bash
ssh "$Z228_VPS" 'ls -dt /root/z228-backup-* | head'            # выбрать бэкап
ssh "$Z228_VPS" 'install -m 755 /root/z228-backup-<дата>/z228.prev /usr/local/bin/z228 && systemctl restart z228'
```

Базу из бэкапа возвращать только с согласия человека (потеряются сообщения после бэкапа) и
только при остановленном сервисе: `systemctl stop z228`, скопировать `z228.db*` в
`/var/lib/private/z228/`, `systemctl start z228`.

## Частые ошибки

- **`Permission denied` при запуске `/tmp/z228-new`** — scp не сохраняет права, нужен `chmod +x`.
- **Собрали под Windows** — забыли `GOOS=linux GOARCH=amd64`. На сервере: `cannot execute binary file`.
- **`CGO_ENABLED=1`** — бинарь потянет glibc с машины сборки. Всегда `CGO_ENABLED=0`
  (SQLite у нас на чистом Go, cgo не нужен).
- **Правка фронтенда «не доехала»** — не пересобрали бинарь (фронтенд внутри) или у людей открыта
  старая страница (нужен F5).
- **Залили, а в git этого нет** — сначала коммит, потом деплой; версия на сервере должна совпадать
  с коммитом в `main`.
- **Чужие коммиты** — другие агенты тоже пушат в `main`. Перед деплоем `git fetch` и
  `merge --ff-only`, иначе выкатите версию без их правок и затрёте их на сервере.
- **Логи:** `journalctl -u z228 -n 50 --no-pager`. Строки `TLS handshake error … unknown certificate`
  — норма (браузеры не доверяют самоподписанному сертификату), не баг.
- **PowerShell портит UTF-8** при правке файлов (`Get-Content`/`Set-Content`) — для текстов
  используйте редактор/инструменты агента, а не PowerShell.

## Git

- Пушим в `main` только fast-forward: `git merge-base --is-ancestor <remote>/main HEAD` должен быть
  успешен. Не `--force`.
- Коммитить код до деплоя; в конце сказать человеку, какой коммит на сервере.

## Десктоп-приложение — отдельно

Деплой сервера приложение не обновляет. Новая версия приложения — это тег `desktop-vX.Y.Z`
(GitHub Actions собирает установщик и `latest.json`, приложения обновляются сами). Выпускать
релиз только по просьбе человека: правки сайта до приложения доезжают и без релиза.
